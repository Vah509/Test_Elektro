# Как это работает

## Поток
```
ZIP в inbox/ (push) ──> workflow site-check ──> process-jobs.mjs ──> site-check.mjs ──> reports/*.md/.json
                                                      │                                      │
                                                      └── Telegram: старт / сводка / файл ◄──┘
                                    коммит отчётов и удаления ZIP (бот)
```
1. **Запуск.** Push файла `inbox/*.zip` в `main`. Коммиты бота (отчёты, удаление ZIP) новый запуск не вызывают.
2. **process-jobs.mjs** берёт все ZIP из `inbox/` по порядку имён. Для каждого:
   - проверяет пути в архиве (разрешены только `jobs/`, `targets/`, `scripts/`, `docs/`, `README.md`; `.github/` через архив менять нельзя);
   - распаковывает в репозиторий;
   - для каждого `jobs/*.json` запускает `site-check.mjs`;
   - шлёт в Telegram сообщение о старте, затем сводку и `.md`-отчёт;
   - **всегда** удаляет ZIP, даже при ошибке, чтобы он не запустился повторно.
3. **Коммит.** Шаг workflow `if: always()` коммитит `reports/`, `jobs/`, удаление ZIP. При конфликте делает `pull --rebase` и повторяет до 5 раз.

## Защита от двух архивов подряд
- `concurrency: site-check` — одновременно идёт только один тест, второй ждёт.
- GitHub держит в очереди **один** ожидающий запуск, лишние отменяет. Поэтому запуск обрабатывает **все** архивы из `inbox/`: отмена запуска ничего не теряет.
- Запуск берёт свежий конец `main` (`ref` = ветка по умолчанию), а не коммит-триггер: отчёты и удаления предыдущего запуска уже учтены.
- Повторы: `reports/processed.json` хранит id выполненных заданий. Тот же id повторно не запустится (придёт «пропущен»). Чтобы повторить — другой id в файле, либо ручной запуск (ниже).
- Telegram сообщает «архив 2/3» — видно, что принято.
- `timeout-minutes: 240` ограничивает зависший запуск.

## Ручной повтор сохранённого задания
Actions → site-check → Run workflow → в поле job: `jobs/имя.json` (без проверки на повтор).

## Режимы (подробно — в job-format.md)
| Режим | Что делает | Ориентир по времени |
|---|---|---|
| `audit` | структурный аудит (HTML, SEO, картинки, sitemap) | 2 мин |
| `standard` | аудит + PSI по представителям типов страниц | 15–35 мин |
| `final` | аудит + PSI по всем страницам, слабые перепрогоняются | зависит от числа страниц |
| `targets` | PSI только по списку страниц | 1–2 мин на страницу-прогон |
| `lab` | локальный Lighthouse на runner'е, без ключа | ~45 с на прогон |
| `plan` | показать, что будет измерено, без замеров | секунды |

Что делает каждый замер: PSI/Lighthouse (оценка, LCP/FCP/TBT/CLS, этапы LCP, главный поток, сторонние скрипты, JS, неиспользуемый код, вес по типам, картинки), CrUX (реальные пользователи, если есть), серверная диагностика (время ответа, `cf-cache-status`, `cache-control`, сжатие у HTML и ассетов), сравнение с прошлыми замерами и блок «Топ причин».

## Файлы результата
`reports/2026-10-30_1430_standard_prod.md` (читать), `.json` (машинный, с полными данными и снимком для сравнения), `.summary.txt` (то, что уходит в Telegram). Время в имени — UTC. Внутри отчёта указано и киевское время.
Сырые отчёты Lighthouse (по 2 прогона на страницу) лежат в Actions → запуск → Artifacts → `raw-lighthouse`, 14 дней. В репозиторий они не коммитятся (большие).

## Ограничения
- **PSI — шумный.** Один прогон может отличаться на 10+ пунктов; поэтому медиана 3 прогонов и пометка шума. Изменение в пределах `max(5, разброс)` считается шумом («~»).
- **Lab ≠ PSI.** Lighthouse на runner'е даёт другие оценки, чем серверы Google. Сравнивать только lab с lab.
- **TTFB и серверные замеры идут из дата-центра GitHub**, не из Украины: смотрим динамику и стабильность.
- **INP** лабораторно не измеряется, только в CrUX, а он при малом трафике может быть пустым.
- **ID аудитов Lighthouse меняются между версиями.** Скрипт берёт запасные варианты, но если какое-то поле в отчёте пустое («—») — откройте сырой JSON из artifact и сообщите Claude: поправим разбор.
- Минуты Actions: у публичного репозитория безлимитные. У приватного — 2000 в месяц.
- `lab` ставит `lighthouse` через `npx` при каждом запуске (по умолчанию последняя версия). Для воспроизводимости можно зафиксировать версию в задании (`lighthouse`).
